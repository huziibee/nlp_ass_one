# Extended task output contract — frozen implemented research decision

## What the brief unambiguously requires

After seeing two contextual symbol/number pairs and a query symbol, Base predicts the query's assigned number. Extended predicts **the query number, the next symbol, and that symbol's number**. The brief deliberately leaves many experiment-design details open.

The **original published Base** implementation accepts a fixed 512-dimensional ResNet18 embedding for each character plus its randomly assigned contextual number, and produces logits for **five numeric labels**. It does **not** already implement a three-output Extended decoder. The original repo is available as an unmodified pinned submodule.

## A necessary design decision

The implemented next symbol `q2` requires a representation and an output probability space. We cannot simply reuse a five-way value softmax for a 50-way or 1,623-way character identity.

| Possible design | Strength | Substantial limitation |
| --- | --- | --- |
| **Context pointer (first or second support character)** | Easy to generalise to unseen character classes; guarantees the symbol refers to the context | Makes invalid-context next symbols impossible by design, potentially eliminating the proposed structural corruption mechanism |
| **Global class-ID symbol head (e.g. 50 training classes)** | Naturally allows off-context output and per-class symbol preferences | Cannot meaningfully predict previously unseen class IDs by the same learned class-ID head; assess label-copy generalisation separately, and state this limitation |
| **Generate feature vectors and retrieve an exemplar** | Works in continuous representation space; could generalise in principle | Adds a decoder and retrieval method with its own learning dynamics and sampling biases |

**Implemented approach (verified):** We built and trained a tractable global 50-class symbol-output head (unmasked categorical samples) for the Extended training-generator analysis, but **do not report next-symbol class accuracy on the 100 unseen final classes** as though the head could solve a zero-shot class-ID prediction. Use a separate contextual-label evaluation for unseen test classes and validation-only analysis of generated symbol structure. The alternative context-pointer head is an explicit useful *negative control*: it removes invalid next-symbol outputs by design, so it should be interpreted as a constraint/mitigation, not direct evidence about unrestricted recursion.

This design is now implemented and validation-audited in `src/extended_omniglot.py` and `scripts/audit_extended_model.py`; see [verified model and G10 findings](EXTENDED_CORRECTNESS_AND_G10_FINDINGS.md).

## Clean distribution needs a declared rule

The brief does not unambiguously specify whether `q2` must be uniformly chosen from the two support symbols, sampled from a wider vocabulary, or generated through some other sequence process. If we choose the two-support-symbol oracle:
- `q2` is equally likely to be the first or second contextual character.
- Its numeric label is given by the label assigned to that character in the current episode.
- A sampled `q2` outside these two characters has **no contextual oracle label**; this is one form of invalid synthetic continuation.

The `src/target_repairs.py` contracts use this proposed two-support-symbol oracle and explicitly do **not** assign an oracle label to an invalid symbol without replacing it.

## The synthetic-data loop also needs a declared rule

Two distinct options:

1. **Full target replacement:** Keep a fixed original-context prefix and train each new model on a synthetic continuation generated by the preceding model. This isolates recursive target-feedback, but **does not recursively alter input-prefix distribution**.
2. **Accumulate or mix original and synthetic samples:** Retain a specified fraction of original data while adding synthetic continuations or full sequences. This may substantially change collapse outcomes; it is not the same experiment as full replacement.

The lecturer's brief uses *adding synthetic data* and leaves this somewhat open. The scientific writeup must describe the actual implemented regime precisely. Ideally compare a matched fixed-G0 synthetic control, clean-only control, and at least one prespecified real/synthetic mixture to distinguish sampling distortion from recursive compounding.

## Evaluation design before training

- **Train:** 50 HDF5 classes and eight training label pairs (one stored exemplar in original Base configuration).
- **Tune:** held-out label pairs, held-out exemplars, and reserved validation classes; do not monitor final test classes.
- **Final test:** 100 held-out classes for Base contextual-label generalisation; use only once after selecting heads/hyperparameters/protocol. Decide separately what outcomes make sense for Extended `q2`, and do not treat already inspected exploratory feature geometry as trained-model final accuracy.
- **Mechanism:** measure previous-token attention, query-key match, value copying, head knockout/keep-only and forced-match repairs on validation, and on protected final cases only after freezing the protocol.
- **Matched controls:** architecture, initialisation seed, batch order, exposure count, temperature and token loss weighting.

The Extended clean generator **chooses one of the two support symbols uniformly** as a documented experimental convention, not a rule specified by the lecturer. Its synthetic output validator temporarily assumes the proposed unmasked 50-training-class output space, allowing off-context symbols but disallowing impossible held-out class logits.
